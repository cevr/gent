"While they may be more efficient, in costs are they more efficient in

26. ~~**Rank by cost per accepted unit, per project and domain, as runs go
    on.**~~ Done: `efficientOrder` in `packages/extensions/src/machines.ts`,
    as the target below says. The orchestrate machine's `rewrite` and
    `dropped` finals do not accept; its recipe names a `domain`. Known
    limits: scores from different scopes are compared as they are; the
    reference price for an unpriced round is Opus-like; a run's own rounds
    never rank it, so a first run keeps one model for every round. The owner: "Each model has jagged intelligence, so perhaps based on
    a project's domain, we can kind of rank efficiency." Before
    (`MachineStore.roundsOf`, `efficientRank`, both deleted) the rank:
    - is keyed by machine name and state only, across every project;
    - measures each model once, then keeps the cheapest for good, with no
      new measure when a model changes or the work moves;
    - counts cost per finished round: a round review sends back still
      counts as finished, and the review rounds it caused (on the strongest
      tier) are not charged to it.

    Target: an implementor model's score is the whole run's spend (every
    role, at each model's quota weight) per accepted unit, keyed by project
    and by a domain the planner names in the unit's spec (for example
    `tui`, `core runtime`, `docs`). A new domain borrows the project's
    score, and a new project the machine's. Older runs weigh less, and the
    rank keeps a small share of rounds on a model that is not the cheapest,
    so a changed model or domain is measured again. The quality rows
    already hold `accepted: { runs, rounds }` per model and state.

    **Easy to dissolve** (owner: "this has to be something that's very
    easy to just dissolve … it might just last a single week"). The rank
    stores nothing: it is one pure function over the run log
    (`machine_steps`) at read time, reading only a recent window, keyed by
    the exact model id, so a new release starts unmeasured. The domain is a
    field of the run's free `input`, not a new column or setting. No score
    table, no owner setting, no migration. Deleting the function falls back
    to the tier's list order.
