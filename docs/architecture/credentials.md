# Credentials

- **Credential slots** — auth keeps the legacy default file/body unchanged and stores named labels under `.slots/<encoded-provider>/<label>` (runtime/provider.ts). CredentialSlot is a constrained nonsecret label (domain/ids.ts); omitted slots mean default. All labels share the existing provider semaphore and cross-process lock. A named-slot directory that cannot be read is logged and hides only its named labels; the default entries still list. One-hop credential owners and legacy aliases are looked up per label; a refresh closes over the physical key and label, and sign-out removes only that label through aliases. providers.<id>.authOrder is optional, nonempty and distinct; config entries that name different orders for one sign-in (an alias and its owner) fail that sign-in only: its resolve, key store and login fail, and its /auth row names the entries (`orderConflict`) with `hasKey` false, while every other provider stays usable. A generic provider is active through a config entry, a default key or a key variable; a key stored only in a named slot gives it an /auth row but serves its models only once its config `authOrder` names that slot. A turn walks the order of the sign-in it dispatches through (`requestCredentialOrder`): each request goes out with the first slot the turn has not left, the turn ledger (`TurnLedger.passedCredentials`) holds the slots it left, a new turn starts again at the first (an unpinned run of a sign-in with a pool at the account its placement chose, below), and a slot that answers serves the rest of the turn. A run whose spec pins a slot (`RunSpec.credentialSlot`, set by `thread.start`'s `account`) walks that slot alone: `requestCredentialOrder` returns the pin as the order of its turns, their handoff summaries and `lastAccountStands`, and a pinned child's first turn starts on its own pin, not where its parent stands, so a refusal on it fails the turn and never moves it; classifier calls and a route's readiness still read the sign-in's order. A turn resumed after a restart reads the `StreamEnded.credential` receipts of its own steps and leaves every slot its order puts before the last one (`TurnLedger.resumeCredential`), as a recovered turn reads its `ModelRouted` route. The slot a request goes out with is recorded when it is chosen: its receipt, its price and a move name that slot, and a config edit during the request changes only the next choice. The turn leaves a slot only on a typed failure before any observable output (`credentialRefusal`): a credential failure a driver proved (`ProviderAuthError.credentialFailure` `Unavailable`, `Rejected` or `UnsupportedModel`, also carried in AiError metadata), an authentication refusal the provider answered over HTTP, an exhausted quota, or a rate limit once its same-slot retries end. A network fault, a defect, an overload, any other refusal and partial output never move it; the last slot of the order fails the turn as before. A move passes an account that filled a quota window of the step's model (lanes.md) and takes one only when every other is filled and the sign-in allows extra usage (`extraUsage`). A handoff summary walks the order under the same rule (`walkCredentials` and `retryOnCredential`, turn.ts, shared with the step): a compactor that fails with the model's failure as `ModelCompactionError.cause` is asked again on the same slot after a transient failure, under the driver's retry policy and with a retry notice, and on the next slot once a failure proves the slot cannot serve, before the next compactor of the chain gets the window; the step after it starts on that slot with no second notice. Each slot tried reserves one model attempt, the user reads a notice that names both labels, and `StreamEnded.credential` (optional, labels only) records the slot the step's last request used. The step's price is the one the catalog lists for that credential (`ModelRegistry.get(model, credential)`), so a subscription sign-in and an API key of one provider price the same model apart. A sign-in is ready, and its catalog lists models, when any slot of its order can serve; its /auth row reads as the first such slot. A named slot with nothing stored fails with `Unavailable`, naming the slot as removed in /auth or never signed in, and never reads the environment. Classifier calls walk the same order: the first slot that builds the model serves, a rate limit that the provider says clears within the driver's retry cap (`RetryPolicy.maxDelay`) and leaves at least the wait again before the call's own deadline gets one more try on the same slot (any other moves on at once), and a proved credential failure of its `decide` call moves the call to the next; the call is priced as the slot that answered lists the model. A stored credential carries `signedInAt` (optional), written when it is signed in or replaced and kept by a refresh and a rename, and a receipt carries it: two receipts are one account when their stamps agree, else when their labels do (`sameCredential`). A step's context window and price are the ones its credential's catalog view lists, and the cold-cache handoff reads the model alone: it waits for the lifetime to lapse, when every account's cache is cold, so a turn that moves past a refusing first slot hands off as any cold turn does. Which slot a turn's next request takes is not known before it goes out, so a model route and an effort route read the cache as cold only on a certain move: the slot of the branch's last receipt left its order, or that slot holds a sign-in with another stamp (`lastAccountStands`, turn.ts); then no effort is held for it; the cache notice names the move (`cache miss after a move from default to personal`) and never `prefix changed`. One rule (`cacheWarm`, turn.ts) reads the cache warm for routes, efforts and placement alike: the account stands, the model is the last call's, and its lifetime has not lapsed. A spawned child's first turn (no request on its branch yet) starts each order where the parent turn that spawned it stands (the parent's newest `StreamEnded.credential` receipts, read once), then its own receipts, but only when the child and the parent walk the same pin (both none, or the same slot): a receipt proves a refusal only on the order the parent walked, so an unpinned named-agent child of a pinned parent starts at the top of its own order; its later turns start at the top of each order, as the parent's next turn does. A sign-in with a pool is not resumed from the parent: the child is placed instead (below). `SessionRuntimeMetrics.lastCredential` folds the newest ended step's model and receipt (none for a step before receipts), and the status row names that label (`via personal`, `via unknown`) beside the model on a sign-in of several credentials. `auth.renameKey` moves a named credential under the provider lock to a label no key of the sign-in holds and no order or pool of the user file or a winning project entry names, and is refused before anything moves when a winning project entry's order or pool names the old label, naming that entry as `auth.setOrder` does (`authSlotRenameRefusal`, config.ts); it relabels it in the order and in every pool the user config holds for the sign-in (`ConfigService.renameAuthSlot`), never copying a project order into the user file. The check, the credential move and the relabel run under the user-config write permit, so an `auth.setOrder` sent during a rename waits for it and never lands between the check and the relabel; `auth.setOrder` writes the order into one user-config entry (the sign-in's owner, alias entries cleared) and keeps each pool to the slots the new order holds (a pool left with fewer than two is dropped), and when a project entry overrides it (an entry for the owner, or an alias entry that names an order) it fails, naming the file, before the user file changes. RPC authorization holds its original method-provider, credential owner, label, inputs and persistence closure through its profile lease; missing leases fail closed. OAuth methods can ask provider-owned prompts. AuthMethod.credentialTarget optionally limits a method to default or named credentials; omission preserves either target. The authorization owner checks the immutable label, and the /auth method picker filters indexed choices by the credential it signs in without changing their original RPC positions. /auth lists a provider's credentials when it has more than its default: numbered in the order a turn walks them, a dash for one the order leaves out, then `+ Add credential` (the default's methods end in that row for a provider with one credential). Shift+↑↓ moves a credential in the order (a move before the list shows the last order write starts from that write), `n` renames a named one, ctrl+x twice removes one and its place (an order the removal would empty stays as written, and the notice says nothing serves until shift+↑ moves the default in or the label signs in again: cleared, it would let the default, which can be a billed environment key, serve alone), and Enter signs it in again; a new label signs in with the named methods (an OAuth method asks its prompts first) and then goes last in the order. An order conflict shows above the rows, and a reorder writes one order. An OAuth sign-in keeps the answers to its method's prompts (`AuthInfo.Oauth.metadata`, read by its driver as `ProviderAuthInfo.Oauth.metadata`) through a refresh, which keeps the held record's, and a rename, which moves the whole record; auth summaries never show them. A named Anthropic credential links a Claude Code config directory (method 2, named credentials only): the link resolves the absolute directory (`path.resolve`; a relative path is refused), reads its login once (a missing or undecodable one is refused, an expired one is accepted), and stores `{ access: "", refresh: "", expires: 0, metadata: { directory } }`. The record stores no token, and an older gent that reads it fails closed on the empty refresh token instead of refreshing a copy; the only token gent's store ever holds for a link is a rotation it has not yet handed back (below). Each request reads the login Claude Code keeps for that directory: on macOS its keychain service `Claude Code-credentials-<first 8 hex of SHA-256 over the directory>`, and only that one, with no file fallback, so the read and the write-back use one entry; elsewhere `<directory>/.credentials.json`. A refresh is direct OAuth only, never the `claude` CLI or the primary entry. A directory's rotation is a state machine gent's credential store persists (`readLinked` and `refreshLinked`, anthropic.ts): `synced`, when the store holds nothing for it, or `pending`, when the store holds a rotation gent spent a token for and has not yet handed back, with the fingerprint (SHA-256) of the source login that spend replaced, its base (`PendingRotation`, at `.rotations/anthropic/<SHA-256 over the directory>` beside the auth entries, owner-only, never listed as a credential and never discarded when it does not decode). It is keyed by the directory, not by label or link, so a rename, a second link, a second label, a new profile or a restart meets the same rotation. A rotation file that does not decode (its read fails `HeldRotationUndecodable`, naming its absolute path) is moved aside before any spend, byte for byte and owner-only, to `<file>.undecodable-<epoch ms>` beside it, which gent never deletes, and in the same locked step a record (`QuarantinedRotation`) takes its place holding that path and, as its base, the fingerprint of the source login gent found beside it: those bytes may hold the only live token whose spend replaced that login, so while the source holds it a read serves it and a refresh spends nothing and fails `Unavailable`, naming the directory and the moved file, and once Claude Code writes another login (a sign-in or its own refresh) the record is forgotten and the slot is synced again; a source signed out moves the bytes aside and keeps no record, a source that cannot be read changes nothing, and a move that fails leaves the file and blocks the login all the same. A link that fails (the directory takes no new name) blocks every login the source holds, a new sign-in included, as each settle finds the file again: a refresh fails `Unavailable`, naming the file and the step that clears it, moving it out of its directory by hand, with no sign-in hint. A link that lands under a record that fails leaves the bytes under both names, and the next move takes that sibling again (the name beside the file with its device and inode), so the bytes keep one other name however often the move is retried. Every read and refresh of a link runs under the store's per-provider lock (the in-process semaphore and the cross-process lock file, inside the cell's lock), so the gent holders over one credential store share one state and one refresh at a time. Two gent processes share that state and that lock only over one credential store: processes with different `GENT_AUTH_DIRECTORY` values share neither. The lock orders gent holders only: Claude Code takes no gent lock, so its refresh and gent's can both spend the base's token, and the loser's one re-read (`afterRefusal`) can come before the winner's write, which leaves the slot `Rejected`. The lock is per provider, so every link of every process over one store waits behind one token request: a waiter polls about 30 s (1500 × 20 ms), and a linked refresh holds the lock through its whole step, which has no single bound: on macOS its deadlines are the keychain account 2 s, the source read 5 s and its write 2 s (a landing is all three, 9 s), and the token POST 15 s (`OAUTH_TOKEN_TIMEOUT`, `postOAuthForm`); elsewhere a landing is the file's read 5 s and its write 5 s (10 s), with no account. The step sums to about 31 s from `synced` (read and account, POST, landing), 33 s from `pending` (a landing that fails, POST, landing; 35 s elsewhere), and 40 s on either when a held rotation lands, or the source moved past it, and the login it serves is expired, so the source is spent again (landing, read and account, POST, landing), plus the store's own disk I/O, which has no deadline. A waiter behind a step longer than its wait fails busy (below), which may pass. A lock another holder keeps for the whole wait fails `CredentialStoreBusy` (the lock file's timeout, typed as `AuthError.lockBusy`): a read serves the credential its cell trusts, and a refresh fails `CredentialRefreshUnavailable` (it may pass) and spends nothing. A refresh failure that may pass fails its request as itself (`explainCredentialFailure`, providers.ts): retryable, with its own message and no network hint, and its retry notice reads that message alone, with no `Internal provider error: ` prefix (`retryReason`, runtime/provider.ts, prefers the credential failure a driver attached to the `AiError`). A read first hands a pending rotation back: it rereads the source and writes the rotation over it only while the source still holds the login at the base; a source that already holds it, or that moved past the base (Claude Code's own refresh or a new sign-in, which wins and serves), ends `pending`, and while the rotation cannot be written (an unreadable source, a failed write) it serves, so the older source login, whose token is spent, never does. Only a missing entry or file, or JSON with no `claudeAiOauth`, is a sign-out: it drops the rotation and fails `Unavailable`, and a removed entry is never recreated. A blob that does not parse (a torn write), a locked or denied keychain or a timeout is unreadable and proves nothing: a held rotation stays held and serves, a synced slot serves the credential its cell trusts, and a refresh fails `CredentialRefreshUnavailable` naming the source as unreadable. From `synced`, a refresh spends the source's token only after it read the source and, on macOS, found the entry's account (`acct`) the write needs, else it fails `CredentialRefreshUnavailable` (it may pass) and spends nothing; a fresh login that is not the one the cell holds serves without a spend. From `pending`, it spends only the held rotation's token, which gent alone holds, and keeps the base; the cell's own token is never sent. Every spend saves `pending` before its write-back, so a failed write, a process exit or a profile rebuild leaves the rotation for the next read of any holder. When the endpoint refuses a token, gent reads the source once more and adopts a fresh login Claude Code wrote meanwhile (its own refresh won the race); otherwise the slot is `Rejected`, and a held rotation stays held until the source moves, so the spent login at its base is never spent again. Four windows stay: a crash between the token response and the save of `pending` loses the rotation (the save is the next step of an uninterruptible one), and the directory then needs a new Claude Code sign-in; the endpoint can spend the token while its response is lost, times out (15 s) or does not parse, and then nothing is held, the next refresh sends the spent token again, the endpoint refuses it, and the directory needs a new Claude Code sign-in; a store that cannot save `pending` while the write-back also fails holds it in its process memory (`serializeAuthStore`) until a write lands or the source moves past its base and the settle forgets it, never for the cell's 30 s lifetime alone, but a process exit before it lands loses it, and another process over the store sees only the disk; and the keychain has no conditional write, so a login or sign-out Claude Code writes between the reread and `add-generic-password -U`, two `security` calls in a row, is overwritten (the file has the same window between its read and its atomic rename). Otherwise Claude Code and gent share one login, as the default slot shares the primary entry with the CLI. A named Anthropic OAuth record with no directory (the owned copy an older gent imported) fails with `Unavailable` and asks to link the directory again in /auth. A linked slot's cell is partitioned by label and link (its `signedInAt` and directory), so a label linked again never answers with the last link's account. The default Claude Code path keeps the unsuffixed keychain service, the `~/.claude/.credentials.json` fallback and the legacy CLI refresh, and its refresh failures carry no `credentialFailure`: its CLI fallback can fail for reasons the account does not cause, so only a request the provider refuses (an HTTP 401 or 403) moves a turn off the default Anthropic account. Existing profile-local Anthropic/OpenAI credential cells and OpenAI account-bound reasoning state are partitioned by label. A store-backed cell serves warm only the sign-in it was read for (`ProviderAuthInfo.signedInAt`, `CredentialStore.signedInAt` in providers.ts): a label renamed away, renamed into or signed in again reads the store on its next request, so the account it held before never answers it. Same-label replacement publishes the owned cell exactly once after successful persistence, under the same raw-write commit mask; source and cell/provider/SQLite acquisition retain caller interruption status. The optional publication effect is bounded cell state only, never I/O or reentrant auth. Unsupported named OAuth cannot become an ambient API key in an API-only owner; default/omitted environment behavior remains. Auth summaries expose labels, auth type, source and availability, never token or directory data. - **Credential placement** — `providers.<id>.authSpread` names a pool of at least two slots of the sign-in's order that it spreads its unpinned runs over (config.ts); without it nothing changes. A pool that names a slot its order does not (with no `authOrder`, the order is the default alone) fails that sign-in only, as conflicting orders do: its /auth row names the entries (`orderConflict`). A rename relabels the pool with the order, and an order write or a removal in /auth takes the slot out of it. Such a run walks the pool, then the rest of its `authOrder` (`requestCredentialOrder`), starting at the account its placement chose (`placementWalk`, turn.ts); a pinned run is never placed and walks its pin alone. A run is placed only where its prompt cache starts over anyway, since a cache belongs to one account and one model: at the first request of a cold turn (a new session, a handoff session, a spawned child, another model than the last call's, or a lapsed lifetime: `cacheWarm` false), at the first request after a window handoff, inside a turn too (the summary stays on the account that holds the window; the step after it is placed, and its window, hints and lifetime are the placed account's catalog entry), and on a refusal that moves the turn (a rate limit past the driver's retry cap, an exhausted quota or a proved credential failure: the account is held until the reset the failure names, else 5 minutes, and the turn ranks the accounts left by the placement rule below; a rate limit or an unsupported model holds the account for that model alone, any other refusal for every model). Past every pool account the turn walks the rest of its order, which is no placement. One rule (`poolStanding`, turn.ts) holds at a turn's start and at a window handoff alike: a run outside the pool stays there, recording nothing, while no pool account is eligible (each held by a refusal or left by the turn), and at the first of those switch points where one is, it returns to the pool, warm or cold (`returned`, `from` the account outside the pool): who pays outranks the cache, and a turn never moves mid-flight for it. A rate limit that clears within the retry cap retries on the same account, and a warm turn stays where it is however uneven the usage; its cache lives as long as the account of its last request lists it. A fork takes the account its copied window is on with no ranking, before any pool rule (outside the pool too, the parent's own pin or fall): a spawned session whose window holds messages copied at create, on its parent's model, or a branch forked from another (`branch.fork`, its own `BranchCreated.parentBranchId`) whose source ran on the model. `CredentialPlacement` (provider.ts, one per server) ranks eligible accounts below their own sustainable live load first, by weekly (`7d`) reset ascending (no weekly reading last), then accounts at or above pace by `load / unit + live`: an account's load is the recorded price of its steps and handoff summaries in the last 7 days, a unit the provider's recorded spend in that window over its sessions (each counted in the hour of its latest priced step, every account included, the ones a refusal left too), and live the sessions whose cache on it still lives (as long as that account lists the cache, from each step's receipt; a cache with no listed lifetime never goes cold, as `cacheWarm` reads it, so its session stays live there until it moves), each at its model's share of a mean run (`runShare`, as admission counts it), and an account's pace, read in runs of the placed model, is turned into mean runs too; with nothing priced or no session counted, the live sessions alone. The account the run's cache or its parent's lives on (same model) is kept only while below pace and within one session of the first eligible account's score. Equal resets and equal scores keep pool order; held accounts walk last. With no known sustainable rate, the original score and preference rules apply. Owner rule (2026-10-21): treat accounts' windows as one pool first. Weekly quota targets 100%; rolling resets set pool pace under the refill ceilings (below). The 5-hour window caps sustainable load; it is never a target to burn or empty. Use the earliest weekly reset first, so its quota is used before it expires. A fresh child is not placed on an account other than its starter's where a sibling was placed and has not ended its first step, so a burst of threads pays one cold start per account. Every receipt of a sign-in with a pool counts, pinned or not; a sign-in with none records no bucket, so a server where nothing spreads and no quota window was read writes no ledger. The hourly buckets are kept in `<data dir>/credential-usage.json` (owner-only, numbers, labels and the ids of the sessions each counts, never a credential), loaded at server start, trimmed to 7 days, written at each hour boundary (when anything changed since the last write that succeeded) and at shutdown; a session the loaded buckets name counts once, in its latest hour, so a session that goes on after a restart is not counted twice; a missing or undecodable ledger starts at zero and never fails a turn, and two gent processes keep separate ledgers (the file is last-writer-wins). The ranking reads gent's receipts and quota windows: Claude Code's own use of a linked account shows in those windows (below). Each placement is a `CredentialAssigned` event naming the pool account it chose (provider, slot, the slot it left, and the reason: `new`, `spawned`, `fork`, `handoff`, `compacted`, `cold`, `refused` or `returned`), written with the receipt of the first step request on that account the provider answered (a part arrived, or the request failed with the provider's response), in the same storage transaction and just before it (`makePublishReceipt`, turn.ts). That request may itself be refused, or interrupted once a part arrived: the provider answered it, and its terminal receipt records the placement. A decision no answered request backs records nothing: a step the model-call budget or the stop check ends before it sends, a request that fails before the provider answers (a sign-in that fails as the request is signed, a lost connection), a request interrupted before its first part, or a turn lost to a restart first; such a step's receipt still names the account it selected, as without a pool, but carries no placement. That can only under-record, so a placement never names an account the run did not send to. A summary request writes no receipt, so a decision first used by one is recorded with the next step's. A turn recovered after a restart reads its receipts alone: its walk stands on the account its own newest receipt ran on, where a handoff reads it, as a live turn's stands where its last move settled, and it is not placed again at its start. A turn with no receipt of its own is placed afresh through the ranking, and so is one whose receipt's account its pool and order no longer name, every pool account held or not: it has no account of its order to stay on, so the rule above does not apply, and with every account held the ranking falls back to the pool's first (`returned`, `from` the receipt's account). Each fresh decision is recorded with its first answered step request's receipt in turn. `SessionRuntimeMetrics.placement` folds the newest one, and `sessionAccount` (domain/agent-loop.ts) reads a session's account and how it came to it: `pinned` by its run spec, `assigned` when its last step went out on its placement, `walked` otherwise, and none while its last step's receipt names no account (a placement alone names none). `session.getSnapshot` answers it as `account`, and `thread.list` names it per thread. Every composition root provides the service: the server's `CredentialPlacement.Live`, and `CredentialPlacement.Memory` (no ledger) in the test actor roots; the turn yields it.
