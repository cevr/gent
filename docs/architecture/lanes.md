# Account lanes

A driver that reads an account's quota windows reports them per step through `ProviderReport.quota` (domain/driver.ts, `reportProviderQuota`), and the loop notes them on the account the step's request went out on (`CredentialPlacement.noteQuota`). Quota state belongs to a sign-in, not to its label: each report, reading and segment carries the stamp of the credential it was for (`AuthInfo.signedInAt`), each lane's accounts carry the stamp the store holds now (`credentialLane`, through `ModelRegistry.stamp`), and placement binds each label to that sign-in. A new sign-in under a label starts with no reading, and a late report of a sign-in its label replaced since is dropped. A rename in /auth (`auth.renameKey`) tells the placement (`renameLabel`): the readings and holds go with the sign-in to its new label, and a late report under the old label counts on the new one. A stamp names a sign-in only under its own label: two labels whose sign-ins share a stamp stay two accounts. The Anthropic driver reads them on a Claude plan sign-in, from every answer, a 429 included (`unifiedQuota`, anthropic.ts): `anthropic-ratelimit-unified-{5h,7d}-utilization` (the fraction used) and `-reset` (epoch seconds), and the account's `-status` and `-representative-claim`; the names are the ones Claude Code 2.1.306 and 2.1.316 read, and an answer with no status says nothing. A refused account (`rejected`, its claim) holds that window, full when no utilization is given, until its reset, and the placement holds the account while that reading stands: the hold is read from the readings, so a server that loads them after a restart holds it too. The OpenAI driver reads them on a ChatGPT plan sign-in, from every Codex answer, a 429 included (`codexQuota`, openai.ts): `x-codex-{primary,secondary}-used-percent` (0 to 100), `-window-minutes` (the window's name, `5h` or `7d`, comes from it) and `-reset-at` (epoch seconds), the names Codex reads (openai/codex `342ed69`); a window at 100% is rejected until its reset, as credits past it are extra usage and never quota, and other limit families (`x-<limit>-…`, single models) are not read. An API key gets none. A driver may also read an account's windows with no step (`ModelDriverContribution.readQuota`, which spends no quota): the server's pool sweep (`sweepPoolQuotas`, provider.ts, a scoped fiber server.ts forks once the launch profile is built, over that profile's registry) reads every slot of every sign-in's `authSpread` through its owner driver, one slot after another, at server start and every 10 minutes, and notes each answer on the sign-in the slot holds now (`noteQuota` with its `signedInAt`), so placement ranks an account no step has run on yet by its week, and admission paces it. A read that fails is logged (`credential-placement.quota-read.failed`) and skipped, never failing a turn or the server; a label with no sign-in and a driver with no `readQuota` are skipped. The Anthropic driver reads a Claude plan sign-in's windows from `GET https://api.anthropic.com/api/oauth/usage?cedar_ember=1` (`readOauthQuota`, anthropic.ts; without the `skip_spend=1` Claude Code 2.1.316 sends on its window-free reads, until a live read proves the windows stay; `anthropic-beta: oauth-2025-04-20`, the Claude Code user agent, no session header, the access token from the same cache its requests use, so a refresh runs under the store lock and an owned label's checks hold; a 401 reads once more on a fresh token): `five_hour` and `seven_day` each `{ utilization: <percent>, resets_at: <ISO 8601> }` become the `5h` and `7d` readings, rejected at 100%, and a window that is null or has no reset reads none. The OpenAI driver reads a ChatGPT plan sign-in's windows from `GET https://chatgpt.com/backend-api/wham/usage` (`readCodexQuota`, openai.ts; the headers a Codex request carries, the access token from the same cache, which serves only the sign-in the read was made for, a 401 reads once more on a fresh token), the endpoint Codex reads for `/status`: the plan's own `rate_limit` has a `primary_window` and a `secondary_window`, each `{ used_percent: <percent>, limit_window_seconds, reset_at: <epoch seconds> }`, the fields of the `x-codex-*` answer headers. A window takes its name from its length in minutes rounded up (`5h`, `7d`), never from its place, so a plan whose limit states a weekly primary window alone reads `7d`, and a usage read and an answer's headers land on the same window; a window that is null or has no length or reset reads none, and `additional_rate_limits` (single models) are not read. Both drivers read through `readPlanUsage` (providers.ts). An API key reads none and sends nothing. The same reads carry each account's banked resets, below. A driver may instead limit a model by what it costs (`ModelDriverContribution.spendLimits`: at most `usd` of list price in any trailing `window`). The OpenCode Go driver sets 20%, 50% and 100% of each model's monthly dollars over `5h`, `7d` and `31d` (`goSpendLimits`, opencode.ts; `OPENCODE_GO_PLAN=plus` reads Go Plus, any other value Go), and none on a free model or on Zen. Gent meters each account's own priced spend on such a model per hour (`noteFuel` with `spendLimitsOf`, a step's and a summary's alike) and reads each limit as that model's window (`meterReadings`): the spend in the trailing window over the limit, rejected at the limit (spend past it is extra usage, never quota) until the oldest hour whose leaving brings it under leaves, and its known spend a floor while an unpriced request falls in it: such a window stays rejected once its known spend reached the limit, and is unread otherwise. A request is priced at what its driver names for it (`requestPricing`, through `requestCost`, provider.ts; a step's, a summary's and `models.decide`'s cost alike), else at the model's list price: the Go driver bills a request past its model's long-context line at that tier's price, and a DeepSeek one double in the plan's peak hours (01:00 to 04:00 and 06:00 to 10:00 UTC, Monday to Friday; `goRequestPricing`). A metered window's fuel per percent is its limit's own (`meterRate`), and under its limit it carries one run at least. A new sign-in under the label starts with no metered spend, and a meter goes with its sign-in on a rename. A server that loads the ledger binds each label to the sign-in of its newest stamped reading or meter, so a meter keeps its sign-in after a restart, and a new sign-in after one still starts with none. A reading may name one model (`QuotaReading.model`): a plan that meters a model apart from the account reports that model's window beside the account's of the same name, and the readings, the segments and the ledger key it apart (`windowKey`). A rejected model window holds the account for that model's runs alone (`meters`, through `isHeld`); its segments count that model's fuel alone (`noteFuel` names the step's resolved model, a summary its own); a start admits against the account's windows and those of the model its route spends on (`LaneRequest.model`; a virtual model's default choice, `routeSpendModel`, turn.ts). `accounts.lanes` lists every window, a model's with its `model`, and counts the account's alone in an account's `sustainable` and the provider's `capacity`; the pool's weekly and five-hour pace reads the account's `7d` and `5h` alone, and a model's window is one of the other window ceilings when a start of that model is admitted. The TUI's binding window still reads every window, a model's among them. Every step and handoff summary on a credential is fuel on that account, pool or not (`noteFuel`): its list price over $5 per million tokens, so one fuel is one input token at that price, with its token classes kept; a price that is unknown, or $0 for tokens spent, is unknown fuel, never zero. Per account window, a segment runs from one reading to the first that moved at least 1% from where it opened, and closes with the fuel spent in it; a reset (its time moved by more than 60 s, or the window fell), a gap over 15 minutes, a refusal or unknown fuel drops it. Fuel per percent is `Σ fuel / Σ points` over the kept segments, each halved per 24 active hours after it; a segment that spent none, or whose move passes its fuel by more than 3 points at the rate of the other kept segments, each fuel at the model weights, is spend outside gent and left out (`outsideShare`); each segment is judged with itself left out, until the kept set holds still; a window with fewer than 2 kept (`QUOTA_JUDGED_SEGMENTS`) keeps none: one judges no outside spend. `band` is `±0.5 / Σ points` kept. A window with no rate of its own reads the provider's. A plan does not bill each model at its list price, so a segment keeps its fuel by model (`FuelSegment.models`) and its edge steps' fuel (`edges`); `fitModelWeights` fits a quota weight per model over the account windows' kept segments: least squares of each move at its window's weighted rate against `Σ weight × fuel`, each row over its edges' rounding variance and its account's window count, a one-point prior at 1, fitted over a 24-hour span with a standard error under 10%, else 1, clamped to [1/8, 8]; windows and weights refit until still (`fitProviderWindows`). `accounts.lanes` reports them (`models`), and each account window its models' fuel per percent (`LaneWindow.models`). Admission still counts runs alike. A window carries `(1 − u) × 100 × fuelPerPct / (fuel per lane-hour × hours to its reset)` runs (a reset that passed reads full, over the window's length); an account the fewest of its windows (0 while held). These per-account rates still decide under-pace placement and reset-first ranking; they do not divide the pool's rolling forecast among accounts. A provider's `capacity` paces its scope (the pool, else the order's first credential) in fuel/hour. Its weekly floor is the largest cumulative in-hand quota divided by time to each reset deadline. Its rolling rate is the in-hand weekly quota plus each fresh week's share inside the next 168 hours (`full × max(0, 168 − hoursToReset) / 168`), divided by 168 hours. The target is `max(floor, rolling)`, capped by weekly and five-hour ceilings. A weekly prefix ceiling divides all fuel available before each reset by elapsed hours, then credits that refill; simultaneous resets share the same pre-refill bound. An account's 5h window counts only to 90% of its fuel, in the window's own pace and in the five-hour ceiling (`FIVE_HOUR_SHARE`, provider.ts), so a burst of running work stops short of the hard limit; a weekly window and a model's own window count to their end. A window at its share carries no run before any rate is read, an account with such a window carries none whatever its other windows' unknown paces, a pool whose every account carries none admits no start, and placement puts an account with no room after every account with some. A turn already running keeps its account until the provider refuses it. The five-hour ceiling includes only accounts with weekly room now, plus a spent week's fresh five-hour room from its reset when that falls within five hours; a reset in six hours adds none. An account that reads no 5h window (a plan whose usage names none) adds its weekly room whole: no short window bounds it, and another account's full 5h window never lowers what it carries. An independently rejected five-hour window still holds until its own reset. Short-window fuel is bounded by weekly room on the same account, so complementary windows cannot create fuel. Every refill is credited after its prefix bound, and refilled short-window fuel must also last five hours. Gent uses a 100% quota target. Every hour counts alike: the floor and the rolling supply spread each window's fuel evenly over the hours to its reset, so the pool spends at a steady rate until its quotas are used up. The one exception is the owner's Sabbath (`sabbath` in the user file: a latitude, a longitude and a time zone; `Sabbath`, config.ts): from Friday's sunset to 30 minutes after Saturday's at that place, the sunset from the sunrise equation (`sabbathAround`, provider.ts). A run a start was admitted to (a thread's round, a child's run) that is running at sunset stops before its next request (`CredentialPlacement.sabbathStop`, `SabbathStop` in turn.ts): its turn ends as at a usage limit, its retry `{ at: the end, cause: sabbath }` (`TurnRetry`, `ErrorOccurred.retryCause`), and a machine reruns the round fresh at the end with no visit or attempt spent. The turn record keeps the admitted lane its turn opened on, with its Sabbath (`TurnRecord.lane`, `TurnLane`, `OpenLane.resumed`): a turn a restart cut opens again on no grant, counts as a run again and stops in that Sabbath all the same; a turn no start admitted keeps none. Such a step asks no classifier first: a virtual model's route and an `/effort auto` pick do not run, and it writes no model-change line. The owner's own turns answer as always. Admission refuses every start then with `LaneUnavailable`, `retryAt` at the Sabbath's end: a new start, a queued one when the Sabbath starts (the queue's alarm serves it at sunset, with no run ending), a grant not yet sent and a start admitted again under its key. The lanes report names the end while the Sabbath holds (`LaneReport.sabbathEnd`), and the band and `gent ctl lanes --line` show `sabbath · no run starts until <end>` as their first row, alone when gent read no quota window. The owner's own turns never ask for a lane, so they answer as always. The weekly floor, the rolling supply and the weekly ceilings count only the hours outside a Sabbath (`openHours`), so the pool spends its week before the Sabbath and after it; the 5h ceiling and the placement order stay on plain hours. The owner's day and night pacing (a `night` setting that weighted night hours and capped a project's night lanes) was removed on 2026-10-26; a user file that still sets `night` loads, the key is ignored and a config write keeps it as written. `capacity = floor(min(target, weekly ceiling, five-hour ceiling, other window ceilings) / fuelPerHour × (1 + leeway))`, with one final floor: the lanes admit a little over the pace (`LANE_PACE_LEEWAY`, owner, 2026-11-01). The leeway is 5% while that pace is at or above the even weekly supply (every account's week, held ones included, over the open hours of the week ahead), 10% at half of it or below, linear between, and 5% with no weekly reading: a slow pace fits few runs, so one run may pass it by more. The orchestrate budget admits Claude agents and Codex turns by the same rule over the same limit (dotfiles `budget.json` `leeway`, `leewayAt`), so the two agree on a start. A supply of none stays none, and `pool-overshoot` counts past the same capacity. Unknown readings or rates keep capacity unknown; an entirely held scope is zero. Explicit credential refusals contribute no forecast; quota rejections contribute their future refill but stay held for present placement. A scope without weekly readings keeps the sum of account minima. Pools with no readings keep stage-0 ranking; accounts of equal score go by weekly reset (no reading last), so the sweep's readings order a pool no step has run on yet. A pinned scope cannot borrow another account's refill. Fuel per lane-hour is measured: a lane that ends adds its fuel and its hours to its provider's burn, the burn before it halved per 24 lane-hours, and a lane with unknown fuel, or of a provider gent read no window of, adds nothing; until the provider saw 1 lane-hour it is the prior, 3.4 M. A lane of a model gent reads a window of adds to that model's burn too (`modelBurns`), and a model's window paces its runs at that model's rate (`modelFuelPerHourOf`): its measured burn once its lanes saw 1 lane-hour, else the prior times the model's price over the reference model's (`priceRatioOf`: its metered fuel over the same tokens at the reference weights, input 1, output 5, cache read 0.1, cache write 1.25), else the provider's. `accounts.lanes` reports it (`fuelPerHour`) with the lane-hours behind it (`laneHours`). `accounts.lanes` (rpc.ts, no session: the accounts are the server's, the scope the launch profile's config) answers each provider gent read a window of, with its `load`. A run's lane is the route its session's turns take (`credentialLane`: the pin, else the pool, else the order's first credential). `CredentialPlacement.admitLane` admits a run that another run starts (threads, through `ExtensionContext.Accounts.admit`), through a fair queue per pool (provider and scope, `laneQueueKey`): the load is the admitted runs (a turn a grant opened or a restart resumed, `running.admitted`) and the admitted starts that share an account with the scope, the asker's own turn left out; the owner's own turns are no load: they spend what the readings show, so the capacity falls as the owner works, and they never take a run's place; the account's windows count each run of that load at its model's share of a mean run (`runShare`: the model's fuel per hour at its quota weight over the provider's, the weights scaled so their fitted mix weighs 1), so a cheap model's run holds part of a lane and the report's `load` is a fraction; a model's own windows count only its runs and starts of that model, whole (each keeps the model its route spends on), and size the account's windows in runs of that model; a start whose share does not fit beside the load under the capacity of either waits in the queue (`LaneAdmission.Queued`, with the waiters ahead of it), and one whose share does not fit even with nothing running is refused for good with `LaneUnavailable` (its `retryAt` the soonest reset or hold end, at least 60 s on), and an unknown capacity admits. The lone start comes first (`loneStart`): with no admitted run on the pool's accounts and an account of the scope that can serve the model now (held by no refusal and no rejected window), a start is admitted whatever the pace, so the pace limits how many run at once, never whether one runs; a scope whose every account is held, or the Sabbath, still refuses it. The queue (`serve`, provider.ts) orders its waiters by the lanes their asking session holds on the provider (open turns and grants of the starts it asked for), fewest first, then by arrival, then by key; a waiter that fits takes a lane (`Admitted` when it got one in its own admission's serve), and the walk starts again. Each serve first drops what time ended (`trim`: an account hold or a reading past its end), and reads each waiter's accounts under the sign-ins their labels hold now (`currentScope`), never under the stamps it asked with: a newer sign-in reported while it waited is what it is served on, and its old stamp never rebinds the label. Strict head of line: behind a waiter the account's windows cannot carry, no later waiter takes a pool lane, so a large run is not passed by small ones; a waiter that waits only for its model's own windows blocks nobody. A waiter whose windows become spent leaves for good with the refusal (`awaitLane` fails). A lane end (`release`), a grant that joins its session's open turn (`openLane`), a freed or lapsed grant, a waiter that leaves (`freeReservation`) and a quota reading (`noteQuota`) each serve the queue; while runs wait, one alarm serves it again at the next window reset or account hold end still ahead after that trim, the change no run's end reports. No timer polls. A waiter keeps its place when admitted again under its key on the same route, and gives it up on another; `awaitLane` waits for its grant and takes it: a taken grant no longer lapses, and holds its lane until its turn opens or a free names it, so a start's send is never raced by its own lapse. `queued` (`ExtensionContext.Accounts.waiting`) reads whether a start waits in its queue under its key and changes nothing; `withdraw` (`Accounts.withdraw`) takes a waiting start out of its queue in one decision under the lock, so a grant and a withdrawal never both win, and its reader hears it holds nothing. A machine round's patience reads one and takes the other ([machines.md](machines.md)). Spent stays a refusal, not a wait: its wait runs to a window's reset, up to a week, and the queue is in memory, so a machine waits it out durably on its run's record (`Waiting`, `lane`). A thread round a spent account refuses waits durably too, on its own row, when the user turned on `wake.autoResume` (threads.md). The queue lives in the placement's memory: a restart starts it empty, and each queued thread round asks again when its starter's loop opens (threads.md). The check reads the capacity unfloored, so a window short of a whole lane still carries a run whose share fits; the report and `LaneUnavailable.capacity` floor it to whole lanes, and the TUI row shows a free count under a tenth as `<0.1` (`laneRows`, apps/tui/src/utils.ts). The pace alone admits a run, and the fair queue orders who goes next: no project holds lanes. The owner's project lane holds (`providers.<owner>.authHold`, which admitted a project's runs up to its hold whatever the pace and kept other work off the held lanes not in use, with a `hold` row per project in the band) were removed on 2026-10-26, as the owner wants a steady flow until the quotas are used up; a user file that still sets `authHold` loads and the key is ignored; a config write keeps it while its provider entry keeps another field, and a write that empties the entry drops it with the entry, since nothing reads it. A project file that sets `extraUsage` is read without it and logs one warning for each file and field set. An admitted or granted start holds its lane under its message id until its turn opens (`openLane`, at each turn's start, a resumed turn included, which also takes a waiting start out of the queue), until its caller frees it (`ExtensionContext.Accounts.cancel`, `freeReservation`: a start that opens no turn of its own, as a round that joins its thread's running turn, one the thread refuses as busy, or one whose copy fails), or, until its caller takes it (`awaitLane`), for 2 minutes as a backstop, when the grant lapses and serves the queue on its own clock (a start that holds it through its preparation, `Accounts.hold`, keeps it while any hold's scope is open, and its 2 minutes start again when the last hold on that admission ends); the lane frees at the turn's end, before its `turnAfter` hooks, and on the turn's exit as a backstop. Only starts wait or are refused: a user's own turn is never queued and never counted as load. The ledger also keeps the latest readings and the segments, 7 days and 500 per window at most, the burn, the model burns, and the meters until their hours leave the longest window, as optional `readings`, `segments`, `burn`, `modelBurn` and `meters` keys, written whenever there are any: an older file decodes with none, and an older binary ignores them. A value the window drops changes the ledger, so the next write leaves it off the file. A SIGKILL loses what changed since the last write (each hour as it closes, and shutdown); the running turns are in memory alone, so a server after a restart counts no lane until a cut turn runs again. An account whose rejected reading meters the step's model is filled for it until the last such reset (`CredentialPlacement.filledUntil`), read for the sign-in the store holds now: one the label replaced since has filled nothing. A step on a filled account leaves it before its request (`meetFullWindow`, turn.ts) for the next account of its order that is not filled, with a notice, and a spread run records the move `filled`. With none left, the turn goes on there only when the user file sets `providers.<id>.extraUsage` (off by default; a project file never sets it), with one notice a turn; else the step stops before its request, naming the first reset (`QuotaWindowsFull`, its `retryAt`). A handoff summary's spend may fill its account: the step after it meets the full window the same way. A moved step's cache is cold on the new account, so its window hands off the history before the turn's prompt when the resend costs more than the handoff (`accountMoved`, `coldHandoffPays`); a small history goes whole. A move back to the account the branch's last request ran on reads that warm cache. A lost login is a sign-in the provider no longer takes: the driver proved its credential absent or its refresh refused (`credentialFailure` `Unavailable` or `Rejected`), or the provider answered 401 to it (`AuthenticationError` `InvalidKey` or `ExpiredKey` with a response, after `authorizedClient` refreshed and sent it once more; `loginLoss` in runtime/provider.ts). A model the account does not serve, a quota, a rate limit, a 403, a missing key and a failure with no response are not losses. The turn records it on the slot its request used (`CredentialPlacement.loseLogin`, from `moveCredential`), pinned run or not, and logs `credential.login-lost` once per loss. The placement holds it in memory, keyed by the sign-in's stamp: a step served on the slot (`noteServed`, from the step's credential walk, neither cancelled nor cut) clears it, a new sign-in on the label (`forget`) clears it, a rename carries it, and a loss reported for an older stamp marks nothing. Quota headers and fuel do not clear it: a refusal carries them too, so a second refusal is no second loss. A summary does not clear it either: a compactor can succeed with no model request. A classifier call or a cache warm that a sign-in refuses records nothing; the next step on that sign-in refuses and records it. Claude Code's own account is `Rejected` when the token endpoint refused every stored refresh token and the CLI fallback failed too, as a linked directory's is. It holds no lane. `accounts.lanes` reports it as `LaneAccount.loginLost` (`since`, `reason`) and lists a provider by its loss alone; the band and `gent ctl lanes --line` print `login! <provider> <slot> <refused|unavailable> · sign in with /auth` after the provider's row, before its holds. A restarted server forgets it until the next refused request.

Banked resets are the plan's own resets an account holds to clear a spent window early: Claude's grants (the claude.ai Resets page) and Codex's reset credits. Only the zero-spend read carries them (`readQuota` answers `{ readings, resets }`; `resets` is a separate optional list of `ResetGrant`, domain/driver.ts, `{ count, expiresAt? }`, never a reading). An absent `resets` says nothing of them; an empty one says the account holds none. The Anthropic driver asks `GET /api/oauth/usage?cedar_ember=1`, the block as TeamClaude asks for it (`src/oauth.js` `USAGE_URL`, `bankedResets`): the `cedar_ember` block counts only while `eligible` is `true` and it lists `grants`; each grant with `resets_left` above 0 is one `ResetGrant`, `ends_at` its expiry; an `ends_at` gent cannot read counts the grant with no expiry. A block that is null, ineligible (`ineligible_reason` such as `cli_version` or `surface`, which the server sends below Claude Code 2.1.280 or off its user agent), has no `grants` or does not parse says nothing. Gent sends 2.1.316 (`MODEL_CONFIG.ccVersion`, the newest Claude Code whose request shape gent matches), above the floor: if the server raises the floor past it, every read of the block is ineligible and reads as no information, the windows still read, and the grants placement holds go at the read-age bound below. Every live grant counts, one usable now or paused alike: the count is what the account holds, as the Resets page shows it. The OpenAI driver reads the answer's top-level `rate_limit_reset_credits.available_count` (openai/codex `backend-client/src/types.rs`, `RateLimitResetCreditsSummary`) as one grant with no expiry, or none at 0, and a negative or non-numeric count says nothing; it does not read `applicable_available_count`, which reads 0 while no window is spent and so would hide a credit the plan holds. The expiry of a credit is only on Codex's detail endpoint, which gent does not read. Both drivers read a count as TeamClaude's `creditCount` does (`resetCount`, domain/driver.ts): a number or a string that holds one, truncated and capped at 99, so a count past a safe integer never reaches the ledger. Each driver decodes the block apart from the windows (`Schema.Unknown`, and `readPlanUsage` decodes the parsed body as it stands), so a block of an odd shape, or a value no JSON schema takes such as `1e999`, reads no resets and never fails the windows. Expiry has one rule, `liveResets` (domain/driver.ts): a grant counts while its `expiresAt` is ahead, and one with none has no expiry of its own. The drivers keep a lapsed grant; placement and the band drop it. Placement holds each account's grants beside its readings (`noteQuota` with `resets`, keyed by provider and label and bound to the sign-in's stamp): a read that names them replaces them, a step's report (which never names them) keeps them, `trim` drops lapsed grants and an account whose read is three sweeps old (`RESETS_READ_LIFETIME_MS`, 30 minutes: only a read refreshes a count, so two failed sweeps in a row keep it, while an account the sweep no longer reads, out of the pool or signed out, or whose answer stopped listing resets goes within half an hour, and a ledger a stopped server left reads none of its old counts), a new sign-in (`forget`) drops them, a rename (`renameLabel`) carries them, and the ledger (`credential-usage.json`, its `resets` key) keeps them across a restart. `accounts.lanes` reports the live grants as `LaneAccount.resets` and lists an account and its provider by its grants alone. The band and `gent ctl lanes --line` print `resets <provider> <slot> <count>, … · next lapses <clock>` after the provider's row and its lost logins (`resetsRow`, apps/tui utils.ts); the band marks it `↺` in muted text; a narrow row drops the lapse, then the provider, then reads the total. An account with none, with only lapsed grants, or out of the provider's scope (as `bindingWindow` and `lanesRetryAt` read it) shows nothing; `gent ctl lanes` keeps every account's `resets` in its JSON. Gent reads and shows banked resets; it never spends one. Spending a reset (TeamClaude's redeem calls, Codex's `codex-reset-credits`) cannot be undone: it stays an owner switch, off by default, planned for later, and no code path sends a redeem request.

The `@gent/login-alert` extension tells the owner away from the band. After each turn it runs the environment's `GENT_LOGIN_ALERT_COMMAND` with `sh -c`, once for each loss `accounts.lanes` lists that it has not alerted yet, with the band's line in `GENT_LOGIN_ALERT` and a 10 s bound. Each command runs on the resource's scope, so a turn's end never waits for one. Only the environment gent starts in sets the command; a project config cannot. With no command it reads no lanes. The alerted losses are server memory keyed by provider, slot and `since`; a loss the report no longer lists is forgotten, so the next loss on that sign-in alerts again. A rename moves a loss to a new slot and a changed extension build starts with no alerted losses, so either can alert one loss twice; a loss a served step clears before the turn ends alerts nothing, as the band no longer lists it. A failed command logs `login-alert.command.failed`. A macOS notification: `GENT_LOGIN_ALERT_COMMAND='osascript -e "display notification (system attribute \"GENT_LOGIN_ALERT\") with title \"gent\""'`.

Pool facts are the part of a server's lanes another machine on the same accounts reads (`plans/cross-machine-pool.md`). The placement keeps them current (`CredentialPlacement.pool`, `PoolFacts` in domain/driver.ts): each locked change builds them afresh and publishes them when they differ, under a higher `seq`, and `boot` (random at start) tells a reader that the `spend` counts started again. Per provider they hold the runs that hold a lane as `lanesHeld` counts them (admitted runs and reserving grants, the owner's own turns left out), grouped by their sorted accounts and model, since a run holds a scope, not one account; per account they hold the warm sessions per model, the fuel and unpriced steps each model spent since `boot` (counted on the label the report named, dropped for a replaced sign-in, kept in memory only), and the reset of the account's weekly window as the provider sent it. They hold no time of the server's clock, so two machines' clocks never meet. `accounts.pool` streams them: the current facts, each change, and the same facts after 30 s with no line, each a whole snapshot, so the reader is the same whichever machine starts the link. Each reader holds one pending snapshot, the newest (a sliding queue of one): a reader that stalls costs one value and a publish never waits under the placement lock. `endPool` ends every stream; the SDK server runs it as its shutdown begins (`endFollowerStreams`), before Bun's listener drain, which waits on each open stream. `gent ctl pool` prints the first; `gent ctl pool --follow` prints each as one JSON line (apps/tui/docs/cli.md).

The peer link counts a second machine's runs and fuel in this server's lanes. `pool.peer` in the user file (`PoolConfig`, config.ts) is a command, an argv array; a project file that sets it gets the user-only warning and is ignored. The server runs it on its own fiber (`followPoolPeer` in runtime/provider.ts): the command's stdin gets this server's facts as JSON lines (`accounts.pool`), and each line of its stdout counts as the peer's facts (`CredentialPlacement.notePeer`). The command is `gent ctl pool --follow` on the other machine through ssh, by its Tailscale name: that call prints its server's facts and sends each line of its own stdin to its server (`accounts.notePeer`), so one link informs both servers. A run that ends, that prints a line that does not decode, or that prints no line for 90 s (three heartbeats: a dead route or a sleeping machine) is stopped, logged (`credential-placement.peer.failed`, with the exit code and the end of its stderr) and runs again after 1 s, the wait doubling to 5 minutes and starting over once a run noted a line and lived a minute; a command that closes its stdout and stays up is stopped 1 s later. The config is read at each run; a `pool.peer` added while the server runs takes a restart. One cache holds the peer's last facts for both links. A line of this server's own boot is dropped; a line of the cached boot with a lower `seq` only keeps the peer heard; any other replaces the cache. The label is the identity: a peer account counts only where the provider's pool (its lane scope) holds the same label. Each label on one side alone is logged once per peer boot (`credential-placement.peer.label-unmatched`), and a matched account whose weekly reset differs from this server's reading by more than a minute (`QUOTA_RESET_TOLERANCE_MS`) is logged once per boot (`credential-placement.peer.week-mismatch`) and still counts.

Runs: admission adds the peer's runs that share a matched account with the request's scope (`peerLoad`) to this server's own (`ownLoad`), each at its model's share, so the `load` of `gent ctl lanes` and the band counts both. The lone start reads that pool load: a peer run is the pool's lone start. Placement ranks an account by the warm sessions of both servers on it (`liveOn`). This server's own facts still list its own runs alone, so the two never echo. A peer line or a reading that lifts a provider's counted load past its capacity over this server's pool is logged once per crossing (`credential-placement.pool-overshoot`).

Fuel: on an account the peer shares (its counted facts list spend or a run on a matched label), a reading that closes a segment holds it pending (`PendingSegment`) for the peer's next line, up to 60 s. That line's rise in spend on the account, per model, since the cached line of the same boot, adds to the newest pending segment of each window the model reaches, and every pending segment then commits. A pending segment no line reaches in 60 s goes: its fuel is unknown, never zero. A reading that opens a fresh segment, or that closes one of unknown fuel, on such an account leaves a placeholder pending, so the next line's rise lands there and not in the point after it. The rise adds fuel, not tokens. A line with no base (the first, a new peer boot, or the first after silence) adds no rise: the open and pending segments of each account the old facts used or the new facts list spend on go. A rename carries an account's pending segments to the new label, and a new sign-in drops them. Before the first line a segment holds this server's fuel alone, so the link should be up before both servers spend. The common order on a live link is facts first (the peer's line arrives before the reading of the point it moved): a steady peer's rise then lands one point late, which a long run conserves and only the edges bias.

The band and `gent ctl lanes` report the peer (`LaneReport.peer`, `peerReport` in provider.ts): the host its last line named (`PoolFacts.host`, the peer machine's hostname to its first dot, `unnamed` when that is empty) and when, its runs on a matched account of this server's pools, and whether it is silent. Each link reports down after 90 s with no line, as the link's own idle stop does: this server's own (`own`, the `pool.peer` command's stdout, counted from the link's start or its last line, so a command that never printed reads down too) and the peer's (`peer`, lines through `accounts.notePeer`, down only once one came in this server run, since nothing tells this server that the peer set a `pool.peer`). The report drops the peer once its facts stop counting (the 30-minute hold below ended) while this server runs no link of its own, so a peer whose owner removed its `pool.peer` leaves the band; while this server's own link runs, the peer stays, with that link down. The band's peer row comes after the provider rows (machines.client.tsx, `peerRow` in utils.ts). Each width shows the most useful facts that fit, in rank: a silent peer's held runs, then the link down, then the age, then the host; the mark and the runs or `unread` always stay. The peer's age is the server's own time less its last line's: the band reads server-now through the connection's one clock offset (`ClientTransport.serverNow`), and the report carries the server's time it was made at (`LaneReport.serverNow`, optional so an older server's report still decodes), which `gent ctl lanes --line` reads in place of its own clock.

Silence: with no line for 90 s the peer turns silent. A watch serves the queue then, logs `credential-placement.peer.silent` once, and drops the open and pending segments of the accounts the peer shares. For 30 minutes after, the peer's last runs still count, and for each provider its facts list this server keeps its own pool load at or under half the capacity, so its starts stay under `min(C − peer runs, C/2)` while the peer may still admit on its side. At the hold's end the peer counts nothing and the queue is served; a lone start still goes in the hold when the pool load is 0. The next line ends the silence and starts a new base.
