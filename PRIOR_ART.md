## Settled

- Line counts across these repos compare different scopes (one file against gent's whole loop). Draw no size conclusion from them.
- gent's step policy (`classifyStep` in `packages/core/src/runtime/turn.ts`, a pure function with a table test) already matches opencode v2: adopted.
- The queue-as-one-module shape (opencode `inbox.ts`, codex `input_queue.rs`) is adopted: `packages/core/src/runtime/agent-loop.ts`.

- The inspected prior-art paths do not persist gent's step-position and in-flight execution receipt contract. Pi 1.0 persists tool/prompt deltas and virtual-model state; those do not supply that contract. gent's exact mid-turn resume (in `packages/core/src/runtime/agent-loop.ts` and `packages/core/src/runtime/turn.ts`) is a capability the owner keeps or drops; a sweep does not decide it.
- The yield of every comparison so far was bugs found while reading gent with the prior art in mind, more than code removed.
- Rejected from prior art: an LLM permission reviewer, a static tool table, a mutex event queue, unbounded steps, whole-log replay, text-blob compaction (`NORTH_STAR.md` → Rejected).

Physical routing/accounting and persisted prompt/tool deltas are capability gaps, with no measured saving claimed.

  Providers: Anthropic takes up to 8,000 px a side, but 2,000 at most when a request has more than 20 images, and 5 MB of base64 an image on Bedrock and Vertex (10 MB direct). Its server scales an image down to 1,568 px or 1,568 visual tokens (standard models), or 2,576 px or 4,784 tokens (Claude 4.7 and later), so a larger image costs only bytes and latency. OpenAI scales to 2,048 a side and 2,500 patches at `high`.
  Decision, by cheap per task and lean core: one fixed profile at the save, not one per model. A `ToolImage` is saved with no model in view, goes to every model the session switches to, and its bytes sit in the cached prefix. A fit per model at request time encodes again on every request or changes the prefix at a model switch; pi and codex scale once for the same reason. The profile is the one the prior art shares: 2,000 px a side (the many-image rule, and below the 2,576 the newer Claude models keep) and 3.75 MiB of bytes (5 MiB of base64). Adopted: Lanczos3. An image inside both limits is stored byte for byte, with no decode. A scaled image keeps its format where the platform encodes it (PNG, JPEG at 80, WebP at 80), and a GIF becomes a PNG of its first frame, as in codex and Claude Code. Past the bytes: JPEG at 80, 60, 40, 20 (Claude Code), then each side x0.75 (pi, opencode). Only bytes no codec decodes fail. `ToolImage` records `originalWidth` and `originalHeight`, and the line beside the image names the original size and the factor in pi's words. The line reads stored fields only, so it stays the same bytes. The codec is Bun's own `Bun.Image` (as in Claude Code), behind `GentPlatform`. It decodes PNG, JPEG, GIF and WebP and works in the compiled binary with no file beside it; photon needs its WASM beside the binary or a patch. Not adopted: a per-model target (Claude Code's 1,568 loses detail on the newer models), palette PNG (one more candidate for a rare case), codex's patch budget (the provider applies it), a developer-role notice (a second message for each image).
  Counsel round 1 (same pass) added three rules. Metadata: of what an encode can carry, `Bun.Image` keeps only the ICC profile (it drops EXIF, XMP and comments), so a 1x1 JPEG with a 4 MiB profile stayed past the limit at every encode. Codex keeps an RGB profile and the EXIF block (`utils/image/src/lib.rs`), Claude Code keeps what `Bun.Image` keeps, and none of them bounds the profile's size. Adopted: a profile that an encode carries at more than a quarter of the byte limit is left out of that encode (the image then reads as sRGB), and an ordinary one stays. The size is measured in each encode, not in the source: a PNG deflates its profile, so counsel round 2 found a 4 MiB profile that took 4,107 bytes in a PNG source and 4 MiB in each JPEG encode; measured in the source, it took 16 encodes and shrank 1800x1800 pixels of noise to 843x843, and measured in each encode it takes 2 and keeps 1800x1800. Factors: pi's one factor, from the width, is wrong for a thin image (1x6000 stored as 1x2000 maps y by 3, not 1), so the line names one factor for each side when they differ at three decimals; three decimals keep a mapped point within one original pixel at a 2,000-pixel edge. Basis: pi applies the EXIF orientation before it measures (pi-mono `1b34779`, `utils/exif-orientation.ts`) but sends an image inside its limits as it is; codex copies the EXIF block. Adopted: every size is of the upright image, and a JPEG its orientation turns goes through the codec, so the stored raster is upright and no provider's EXIF handling matters. Cost: the ladder is 24 side bounds of 4 or 5 encodes (96 to 120), and the codec cannot stop an encode it has started; with the profile bound measured in each encode, an encode keeps at most a quarter of the limit for the profile, and JPEG at quality 20 fits 2,000 x 2,000 pixels of noise in under 0.8 MB, so the real codec fits every image at the first side bound in at most 5 encodes, and the smaller bounds stay as a guard.
